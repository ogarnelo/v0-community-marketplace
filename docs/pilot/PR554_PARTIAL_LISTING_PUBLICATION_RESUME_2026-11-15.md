# WETUDY — PR554 · Recuperación ante publicación parcialmente confirmada
15/11/2026. En la publicación, PostgreSQL guarda primero `listings` y después `listing_photos` en dos operaciones distintas. Si el INSERT del anuncio confirma, pero la segunda operación falla, la UI anterior mostraba «No se pudo publicar» y permitía volver a pulsar Publicar: **creaba anuncios duplicados** pese a existir el primero.

La solución sigue el commit real: `committedListingId` solo se establece después de INSERT de `listings` sin error. Si falla cualquiera de las operaciones posteriores, se navega directamente al editor del mismo ID con `?photosPending=1` en vez de invitar a crear un segundo anuncio. El editor requiere sesión y propiedad antes de mostrar una advertencia fija: «El anuncio ya está creado, pero no se pudieron terminar sus fotografías. Revisa y guarda las fotos aquí; no vuelvas a publicar el anuncio». El indicador de URL no contiene PII ni se refleja como texto arbitrario. Los errores de publicación previos a INSERT mantienen su mensaje genérico.

**Alcance y límite:** el cambio reduce duplicados y confusión del vendedor, pero no convierte las dos operaciones SQL en una transacción atómica. Si el INSERT de `listings` devuelve un error por fallo de red tras commit real, no se puede inferir con seguridad si se creó la fila: el caso ambiguo requiere conciliación por ID/idempotencia en servidor. Igualmente puede quedar una fila sin registros `listing_photos` hasta que el vendedor corrija el anuncio. No borrar objetos Storage después de una confirmación parcial, porque `listings.photos` podría referenciarlos.

Siete contratos Node verifican sintaxis, orden de commit, redirección sin duplicación, protección de propiedad, aviso fijo y ausencia de limpieza destructiva tras commit. CI y Vercel preview necesarios. No se leen ni se modifican anuncios reales durante las pruebas; no modifica permisos, RLS, Stripe o pagos. AMPA 0/3, DR integral pendiente, NO-GO apertura.
